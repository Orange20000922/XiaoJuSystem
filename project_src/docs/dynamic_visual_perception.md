# 动态视觉感知模块技术文档：用于 AI 陪伴 / 教育智能体的低成本实时事件检测与关键帧提取

## 1. 概述

本文档描述了一套面向 AI 陪伴或教育智能体的动态视觉感知方案，目标是在消费级硬件条件下，以较低成本完成**实时视频流中的显著事件检测、面部表情识别、轻量时序分析与关键帧提取**，并将高信息密度的视觉片段交给后续本地响应模块或云端多模态大模型进一步理解。

这一方案适用于“小橘”这类具有长期陪伴、教育互动和多模态情感感知需求的智能体系统。它并不试图在本地完成完整的视觉语义理解，而是采用一种更符合现实资源约束的分层策略：

> **本地做轻量、实时、通用的感知与筛选，云端做复杂、深度、语义化的理解。**

其核心价值在于：

- 避免把连续视频流直接送往云端，显著降低推理成本
- 在普通 CPU 或入门级 GPU 上保持实时性
- 为陪伴场景中的“表情变化”“动作变化”“场景变化”提供结构化事件输入
- 为后续记忆系统、情绪状态机和云端多模态模型提供高质量关键帧

---

## 2. 设计目标

本模块未来应满足以下四个目标。

### 2.1 通用性

模块不依赖单一场景，不仅能处理“人是否出现”，还应能检测：

- 物体进入画面
- 用户大幅动作
- 场景光照突变
- 面部表情变化
- 轻量时间序列动作变化

也就是说，它应当是一个面向真实交互环境的通用视觉事件门控器，而不是某一个狭窄任务上的专用分类器。

### 2.2 实时性

在普通消费级硬件上，本模块应尽量将单帧处理延迟控制在低水平，避免成为主交互流程的瓶颈。

理想目标：

- 传统方法路径：CPU 单帧处理通常在毫秒级
- 轻量 CNN 路径：GPU 单帧推理在数毫秒级
- 总体端到端感知延迟尽量控制在 `30ms` 以内

这样系统才能在陪伴或课堂互动场景中保持自然反馈。

### 2.3 低成本

视觉模块不是用来“理解一切”，而是用来筛掉绝大多数无意义输入。目标是通过两级筛选，使云端多模态 API 调用频率降低到可接受范围，例如：

- 每分钟 `1~2` 次以内
- 月度成本控制在个人项目可承受范围

### 2.4 可扩展

模块必须具备渐进升级能力：

- 从纯传统视觉方法起步
- 再加入轻量 CNN
- 后续再接入轻量时序模型
- 最终形成“事件检测 -> 关键帧筛选 -> 时序理解 -> 云端语义理解”的完整路径

这使得系统既能快速落地，又不阻碍后续性能升级。

## 3.2 模块间分工

整个视觉链路可以分成三层：

1. **低成本事件筛选层**
   - 负责从连续视频流中找出“可能有意义”的片段
   - 以传统方法和轻量模型为主

2. **中间缓冲与时序分析层**
   - 负责在短时间窗口内聚合多个事件帧
   - 可选地做轻量时间模式判断

3. **高层语义理解层**
   - 由云端多模态模型承担
   - 对关键帧、时序片段和上下文做深层解释

这种分层结构的关键在于，越靠近输入端的模块越便宜、越实时；越靠近语义端的模块越昂贵、但触发频率越低。

## 4. 模块详细设计

## 4.1 大范围事件检测

### 4.1.1 设计目的

这一模块用于捕捉画面中的显著变化，例如：

- 有人进入或离开画面
- 用户挥手、抬手、站起
- 场景突然切换
- 灯光快速开关
- 大面积物体移动

同时，它需要尽量过滤掉：

- 树叶抖动
- 摄像头轻微噪声
- 缓慢光照变化
- 边缘区域的小范围无意义变化

### 4.1.2 传统方法路径（极轻量，无需 GPU）

对于第一阶段原型系统，优先推荐传统视觉方法，因为它们：

- 实现简单
- CPU 开销极低
- 无需训练数据
- 调参直观

#### 方法 A：帧间差分 + 运动面积

基本流程：

1. 当前帧转灰度
2. 与上一参考帧做绝对差分 `absdiff`
3. 对差分图做阈值二值化
4. 统计非零像素占比
5. 占比超过阈值则触发事件

典型阈值可先设在 `5%~10%` 区间，根据场景再调。

#### 方法 B：灰度直方图差异

计算相邻帧的灰度直方图差异，如卡方距离或 Bhattacharyya 距离。适合捕捉：

- 场景明暗突变
- 摄像头视角大幅变化
- 背景整体改变

#### 方法 C：边缘密度变化

对图像做 Canny 边缘检测，再统计边缘像素密度变化。适合检测：

- 新物体进入
- 人体轮廓变化
- 背景结构变化

### 4.1.3 轻量 CNN 路径（可选，利用 GPU）

在有入门级 GPU 的条件下，可用轻量 CNN 做二分类：

- 当前帧是否值得关注
- 当前变化是否属于有效事件

可选模型：

- `MobileNetV3-Small`
- `EfficientNet-Lite0`
- 自定义 Tiny CNN

输入建议：

- `224x224 RGB`

输出建议：

- `event_prob`
- `event_type_hint`（可选）

这一方案的优点是：

- 更鲁棒
- 可学习复杂的“有效变化”分布
- 比规则阈值更能抑制误报

### 4.1.4 建议策略

前期建议采用“传统方法为主、CNN 为辅”的混合策略：

- 默认用传统方法做高频初筛
- 只有传统方法触发后，才让轻量 CNN 做二次确认

这样可以同时兼顾：

- 高实时性
- 低算力占用
- 较低误报率

## 4.2 面部检测与表情识别

## 4.2.1 设计目的

陪伴与教育场景中，用户面部表情往往比一般动作更能直接反映交互状态。例如：

- 微笑：正向反馈、轻松状态
- 皱眉：困惑、不满、思考
- 惊讶：意外、兴趣提升
- 悲伤 / 低落：需要安慰或调整对话策略

因此，系统需要一个低成本的人脸与表情通道，为情绪感知提供额外输入。

### 4.2.2 面部检测

建议优先考虑轻量化检测器：

- `YuNet`（OpenCV 自带，轻量、方便部署）
- `RetinaFace` 轻量版（精度更高，但成本略高）

输出：

- 人脸边界框
- 可选关键点
- 检测置信度

若一帧中存在多人，可先按以下规则选主脸：

- 面积最大
- 最靠近画面中心
- 与上一帧追踪目标 IoU 最大

这样可保证模块主要关注“当前交互对象”。

### 4.2.3 表情分类

在人脸区域上运行一个极小表情分类模型。

建议初始类别：

- neutral
- happy
- sad
- angry
- surprise
- fear
- disgust

输入建议：

- `48x48` 或 `64x64` 灰度图

模型可以是：

- 小型 CNN
- MobileNet 裁剪版
- ONNX 化轻量表情分类器

### 4.2.4 触发策略

并不是每一帧的表情都要写入事件缓冲区，建议满足以下条件时才记为有效事件：

- 表情分类置信度 > `0.7`
- 与上一稳定表情不同
- 或同一表情强度显著变化

例如：

- `neutral -> smile`
- `smile -> surprise`
- `neutral -> frown`

这比逐帧记录更符合实际使用需求，也能大幅减少冗余视觉事件。

### 4.2.5 与现有情绪系统的关系

视觉表情不应直接替代现有的文本情绪系统，而更适合作为一个额外输入源：

- 文本情绪来自 BERT / LLM
- 语音情绪来自 ASR / SER
- 视觉情绪来自面部表情识别

未来可以采用简单加权融合，使整体情绪判断更稳健。

## 4.3 周期性采样

### 4.3.1 目的

并不是所有重要信息都来自“突发事件”。有些环境信息本身没有明显变化，但对长期理解仍然有价值，例如：

- 用户长期静坐学习
- 长时间平静表情
- 环境背景变化缓慢
- 某个物体持续存在于桌面

因此，系统应增加低频周期性采样机制。

### 4.3.2 采样策略

建议每 `1~2` 秒采样一帧，作为低优先级背景帧写入事件缓冲区。其优先级低于：

- 大范围事件帧
- 表情变化帧

### 4.3.3 作用

周期性采样的主要价值包括：

- 提供环境上下文
- 为长期记忆提供背景片段
- 避免系统只关注“变化”而丢失稳定状态信息
- 在完全无显著事件时，仍为云端总结提供最低限度输入

---

## 4.4 事件缓冲区

## 4.4.1 设计目的

事件缓冲区用于在短时间窗口内收集“可能有意义的帧”，避免系统因为单帧触发而过于敏感，也为后续时序理解提供最小序列。

### 4.4.2 数据结构建议

建议采用**环形缓冲区**，保存最近 `1` 秒内的视觉事件。每个元素可以包含：

```json
{
  "timestamp": 1710000000,
  "frame_path": "...",
  "event_type": "face_expression_change",
  "confidence": 0.88,
  "priority": 2,
  "bbox": [x1, y1, x2, y2]
}
```

### 4.4.3 写入来源

缓冲区中的帧主要来自三类：

- 大范围事件检测触发帧
- 表情变化显著帧
- 周期性采样帧

### 4.4.4 刷新条件

建议满足以下任一条件时触发后续处理：

- 缓冲区累计帧数 >= `3`
- 从第一帧开始已满 `1` 秒
- 出现高优先级事件，如强烈表情突变

### 4.4.5 作用

事件缓冲区相当于视觉模块的“短时工作记忆”，它可以：

- 聚合多个事件，避免误判
- 为时序模型提供输入序列
- 为云端多模态模型提供多张关键帧
- 为本地规则系统提供事件统计特征

---

## 4.5 轻量级时序模型（可选）

## 4.5.1 引入目的

在很多场景中，单帧并不足以说明问题。真正有意义的是“变化过程”，例如：

- 先皱眉再微笑
- 连续挥手两次
- 从低头到抬头
- 表情逐渐变得紧张

这些都属于时序模式识别问题。

### 4.5.2 可选模型

如果硬件允许，可以在事件缓冲区之上加入轻量级时序模型，例如：

- `TSM-Nano`
- `X3D-S`
- 极小型 3D CNN
- CNN + Temporal Pooling 的简化结构

输入建议：

- 连续 `8~16` 帧
- 尺寸 `112x112`
- 覆盖 `0.5~1` 秒时间窗口

### 4.5.3 输出类型

可输出：

- 动作类别
- 表情变化模式
- “是否值得上传云端”的时序得分
- 简单结构化描述，例如“连续两次挥手”

### 4.5.4 使用建议

这一模块属于**增强项**，不建议作为第一阶段必需功能。原因是：

- 训练与标注成本更高
- 推理成本显著高于单帧模型
- 前期系统主要瓶颈往往不是“模型太弱”，而是“输入触发逻辑还不稳定”

因此更适合在事件筛选和表情检测稳定后，再逐步接入。

## 4.6 本地响应与云端调用决策

## 4.6.1 本地简单响应

并不是所有视觉事件都需要走云端。对于部分高置信、低歧义事件，可以直接触发本地简单响应，例如：

- 检测到微笑："你笑起来真好看"
- 检测到挥手："你好呀"
- 检测到用户长时间低头："是在认真看什么吗？"

这种本地响应方式有几个优点：

- 延迟低
- 零额外 API 成本
- 可增强系统即时反馈感

### 4.6.2 云端复杂语义理解

对于以下情况，更适合调用云端多模态模型：

- 本地模型无法稳定判断
- 同时存在语音、视觉和上下文信息，需要联合理解
- 事件具有复杂语义，例如“用户似乎焦虑但又在犹豫是否开口”
- 需要生成自然、上下文一致的回复

### 4.6.3 云端输入建议

可将事件缓冲区中筛出的关键帧打包后发送，建议：

- 最多 `3~5` 张关键帧
- 附带最近 `1~2` 秒音频片段或 ASR 文本
- 附带当前对话上下文
- 附带最近一次情绪状态摘要

如果本地没有时序模型，也可以直接把多张帧顺序发送给云端，让大模型自行理解时序关系。

### 4.6.4 降级策略

建议明确以下降级路径：

- 时序模型不可用 -> 直接上传多张关键帧
- 面部检测失败 -> 仅依赖大范围事件检测与周期采样
- GPU 不可用 -> 退回纯传统方法路径
- 云端不可用 -> 仅保留本地简单响应与状态更新

## 5. 性能与硬件适配

## 5.1 目标硬件条件

本模块面向以下典型环境设计：

- 普通笔记本 CPU
- 入门级 GPU（如 RTX 5060 / 同级别）
- `8GB~16GB` 内存
- 普通宽带网络

## 5.2 性能预期

| 硬件 | 配置 | 预期性能 |
|---|---|---|
| CPU | 2.5GHz+ 4核 | 传统事件检测 + 面部检测（CPU 模式）可实时 |
| GPU | RTX 5060 (8GB) | 所有轻量 CNN 模块可实时，总延迟尽量控制在 30ms 内 |
| 内存 | 8-16GB | 模型加载 < 500MB，缓冲区占用较低 |
| 网络 | 普通宽带 | 云端调用频率 < 2 次 / 分钟，流量可控 |

## 5.3 分阶段部署建议

### 轻量原型版

- 帧差检测
- 周期性采样
- 无时序模型
- 无表情识别或只做 CPU 面部检测

### 平衡版

- 帧差检测 + 轻量人脸检测
- 表情识别
- 事件缓冲区
- 云端多帧理解

### 增强版

- 二级筛选（传统方法 + CNN）
- 表情识别 + 时序模型
- 本地快速响应
- 与记忆 / 情绪系统深度耦合

## 6. 与现有 AI 陪伴系统的集成方式

当前视觉模块的输出可以通过三种方式接入现有后端。

## 6.1 作为结构化事件输入 LLM 路径

可以将视觉结果包装成类似教师消息或系统事件，例如：

```json
{
  "role": "user",
  "content": "[视觉事件] 用户微笑了，强度 0.7"
}
```

再通过现有对话接口进入推理管线。这种做法的优点是：

- 接入简单
- 复用现有对话系统
- 不需要立即改动底层架构

## 6.2 直接注入情绪状态机

视觉事件也可以作为低延迟情绪刺激信号，例如：

- 微笑 -> valence 正向输入 `+0.2`
- 皱眉 -> valence 负向输入 `-0.1`
- 惊讶 -> arousal 增强

这样可以在不经过完整 LLM 推理的情况下，先更新本地情绪状态。

## 6.3 写入记忆系统

视觉事件可写入长期记忆层，作为跨时间上下文的一部分，例如：

- “今天下午用户多次微笑，整体状态轻松”
- “某次提到考试时出现明显皱眉”
- “学习时长较长，期间表情较稳定”

这类视觉记忆未来可与文本、语音记忆一起参与召回。

## 6.4 推荐集成顺序

建议按复杂度逐步接入：

1. 先把视觉结果作为普通事件送入 `AgentLoop`
2. 再把部分高置信视觉事件映射到情绪状态机
3. 最后再将筛选后的视觉摘要写入记忆系统

这样风险最低，也最容易调试。

## 7. 实验设计与验证方法

## 7.1 数据来源

可使用两类数据：

- 公共数据集：
  - `FER2013`
  - `AffectNet`
  - 动作识别公开子集
- 自行录制数据：
  - 日常陪伴互动视频
  - 课堂 / 学习场景视频
  - 面向目标人群的小样本数据

对项目原型而言，自录数据往往比纯公开数据更贴近真实使用场景。

## 7.2 评价指标

建议至少评估以下四类指标：

### 事件检测效果

- 准确率
- 召回率
- 误报率

### 表情识别效果

- 分类准确率
- 高置信事件提取准确率

### 成本控制效果

- 云端调用频率下降比例
- 平均每分钟上传帧数
- API 成本估计

### 用户体验效果

- 响应是否及时
- 系统是否显得“看到了用户”
- 误触发是否令人困扰
- 主观满意度评分

## 7.3 预期目标

在典型场景中，本模块希望达到如下目标：

- 事件检测召回率较高
- 云端调用减少 `90%` 以上
- 用户主观满意度达到较高水平
- 本地处理对主交互线程影响较小

## 8. 未来展望

## 8.1 更强的本地时序理解

当硬件升级后，可逐步引入更强的视频时序模型，例如：

- 是否进入更敏感或更节能模式

这会使视觉系统从“被动检测器”逐步升级为“带有策略的注意力系统”。

## 9. 可行性分析、ROI 判断与推荐落地路径

基于当前项目的已有能力与实际资源约束，可以对本模块做出更明确的判断：**动态视觉模块整体可行，但应优先做“本地轻量筛选 + 云端视觉语义分析”，而不是一开始就在本地追求高精度、全语义的视觉理解。**

### 9.1 可行性判断

从工程实现角度看，模块内部各部分的可行性并不相同。

#### 9.1.1 高可行部分

以下部分适合优先落地：

- **帧差 / 大范围事件检测**：实现简单、CPU 开销极低、无需训练数据，是当前阶段 ROI 最高的能力
- **人脸检测**：技术成熟、部署稳定，能够让系统从“看场景”升级为“看用户”
- **关键帧缓冲与事件聚合**：属于标准工程组件，实现确定、对整体链路价值很高
- **事件驱动的云端 Vision LLM 分析**：当前系统已经具备 vision client 与主 LLM 协作模式，扩展成本相对较低

#### 9.1.2 中等可行部分

以下部分可以做，但建议保守设计：

- **粗粒度表情变化检测**：例如 positive / neutral / negative，或 smile / non-smile 这类低类别任务
- **视觉结果注入情绪状态机**：适合作为弱信号，而不是硬性覆盖文本 / 语音情绪判断
- **视觉观察写入记忆系统**：适合写入经过抽象和压缩后的观察结论，而不是原始逐帧事件

#### 9.1.3 当前阶段不建议优先投入的部分

以下部分虽然技术上并非不可做，但在当前阶段投入产出比较低：

- **七类及以上精细表情分类**：真实场景中精度容易受到摄像头角度、分辨率、光照和数据分布差异影响
- **本地轻量时序模型**：训练与标注成本高，真实收益未必明显优于规则系统
- **纯本地复杂心理状态推断**：例如直接判断“焦虑、犹豫、疲惫”等高语义状态，容易产生误判

换言之，本地模块更适合回答“发生了什么变化”，而不适合过早承担“这个变化意味着什么”这一层解释任务。

### 9.2 ROI 判断

如果从陪伴体验、比赛展示价值、工程复杂度和系统稳定性综合评估，本模块的 ROI 呈现明显分层。

#### 9.2.1 高 ROI 能力

以下能力最值得优先实现：

- **大范围运动检测 + 关键帧提取**
- **人脸检测 / 用户是否在场判断**
- **事件驱动的云端视觉分析**
- **将视觉分析结果转化为主系统可消费的信号**

这些能力带来的主要收益包括：

- 让系统表现出“它真的在注意用户”的存在感
- 显著降低连续视频直接上云的成本
- 为主 LLM、情绪状态机和记忆系统提供高价值环境线索
- 在比赛或演示中形成完整的多模态智能体叙事闭环

#### 9.2.2 中高 ROI 能力

以下能力有价值，但应在前述链路稳定后再引入：

- **粗粒度表情变化检测**
- **视觉结果作为弱情绪信号调节对话风格**
- **视觉观察的长期画像化总结**

它们能增强陪伴拟真度和教育场景中的学习状态理解，但不应成为第一阶段的核心阻塞项。

#### 9.2.3 低 ROI 能力

以下方向在当前阶段边际收益较低：

- **高类别数的本地表情识别**
- **本地复杂动作时序建模**
- **本地预定义视觉回复系统**

原因在于：

- 开发与调参成本高
- 误判风险会显著影响体验
- 用户实际感知到的提升未必与工程投入成正比

因此，本模块最优路线不是“把本地视觉做深”，而是“把本地视觉做轻、做稳、做成高质量上游筛选器”。

### 9.3 推荐落地架构

结合当前项目的实际代码结构，最推荐的不是“本地直接产出视觉结论”，而是如下链路：

```text
本地视频流
→ 轻量事件检测（帧差 / 人脸 / 可选粗粒度表情）
→ 关键帧 / 短帧片段筛选
→ 事件聚合与去重
→ 云端 Vision LLM 分析变化含义
→ 输出结构化观察结果
→ 分流到主 LLM 注入信号 / 情绪状态机 / 长期记忆
```

这一路径的关键优势在于：

- 本地只承担低成本、高频、确定性的感知任务
- 云端只处理少量高信息密度视觉输入
- 视觉语义解释可以复用现有的 vision-client + 主 LLM 协作模式
- 失败时容易降级，不会破坏主对话链路

### 9.4 Vision LLM 的推荐职责

在这一架构中，云端视觉模型最适合承担的角色是：

- 分析筛选后的关键帧或短序列
- 判断画面中发生了哪些**事实层变化**
- 给出低强度、可约束的**状态提示**
- 生成是否值得写入记忆的候选总结

推荐优先让 Vision LLM 输出以下三层内容：

1. **事实层**
   - 用户坐在桌前
   - 用户低头看向桌面
   - 画面中出现一本打开的书
   - 用户离开了座位

2. **弱解释层**
   - 可能在阅读或学习
   - 可能刚结束当前动作
   - 可能重新回到设备前

3. **记忆候选层**
   - 用户在书桌前持续阅读，状态较平稳
   - 提到某话题时用户出现明显表情变化

应尽量避免直接让视觉模型输出强心理推断，如“焦虑、犹豫、压力很大”等。这类结论可以作为内部低置信提示，但不应未经筛选直接进入长期记忆或主回复。

### 9.5 与主系统的信号分流建议

视觉分析结果不应全部按同一种方式注入系统，而应根据用途分流：

#### 9.5.1 注入主 LLM 的短期信号

适合以下信息：

- 用户刚刚抬头看向屏幕
- 用户露出明显笑容
- 用户离开了座位后又返回
- 桌面上出现了新的学习材料

这类信息应作为**短期上下文提示**影响当前轮次或下一轮的语气、关注点和主动性判断，而不是无条件改写用户输入主语义。

#### 9.5.2 注入情绪状态机的弱刺激

适合以下低维度映射：

- 微笑 -> 轻度正向 valence
- 皱眉 / 明显困惑 -> 轻度负向 valence
- 突然抬头 / 明显动作变化 -> arousal 增强

这里应坚持“弱刺激”原则，避免视觉信号压倒文本与语音。

#### 9.5.3 写入记忆系统的长期观察

只建议写入以下类型的内容：

- 重复出现的稳定行为模式
- 高情绪显著事件
- 对教育任务或陪伴关系真正有意义的视觉观察总结

不建议把逐帧视觉事件直接写入长期记忆，否则很容易污染 L3 / L4，降低召回质量。

### 9.6 推荐实施顺序

基于 ROI 和当前架构，推荐按以下顺序推进：

#### 第一阶段：最小可行版本（MVP）

- 帧差 / 运动检测
- 人脸检测
- 关键帧缓冲与冷却窗口
- 把筛选结果发送给 Vision LLM
- Vision LLM 输出简洁观察文本或结构化摘要
- 将结果作为短期提示注入主 LLM

这一阶段的目标不是“精准识别用户心理”，而是先让系统获得稳定的“看见变化并理解变化”的能力。

#### 第二阶段：状态联动增强

- 加入粗粒度表情变化检测
- 将部分视觉信号作为弱刺激注入情绪状态机
- 对高价值视觉观察做压缩总结后写入记忆系统

这一阶段开始体现“视觉影响人格状态与长期关系”的效果。

#### 第三阶段：选择性增强

- 根据真实使用数据判断是否需要轻量 CNN 二次筛选
- 评估是否真的有必要加入本地时序模型
- 仅在明确收益成立时，再继续提升本地视觉复杂度

这意味着本地视觉复杂度应由真实场景数据驱动，而不是一开始就设计得过深。

## 10. 结论

本文档提出了一套面向 AI 陪伴 / 教育智能体的动态视觉感知方案。该方案通过**传统视觉方法、轻量 CNN、事件缓冲与可选时序模型**的分层设计，在有限硬件条件下实现了：

- 通用的视觉事件检测
- 低成本的关键帧筛选
- 对面部表情与动作变化的基础感知
- 向云端多模态模型高效输送高信息密度输入

它不是要在本地复制完整视觉大模型，而是为系统补上一双**足够轻、足够快、足够实用的“眼睛”**。

对于个人开发者、学生团队和比赛型项目而言，这种方案兼顾了：

- 可实现性
- 成本可控性
- 模块可扩展性
- 与现有陪伴系统的良好兼容性
